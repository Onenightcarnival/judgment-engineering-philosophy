# 推导先于观察

设计有两种依据。观察回答"别人怎么做"，推导回答"这样做必然会怎样"。

能推导的地方，不靠观察。

## 两种依据

| | 观察 | 推导 |
|---|---|---|
| 回答的问题 | 别人怎么做 | 这样做必然会怎样 |
| 需要的前提 | 找得到先例 | 懂机制 |
| 给出的保证 | 先例在它的条件下成立过 | 前提成立，结论就成立 |
| 失效的时候 | 条件变了，没人察觉 | 前提错了 |

观察到的做法带着它原来的条件。做法被抄走，条件留在原地。

## 三步

1. 列出选项。
2. 推演每个选项的必然后果。
3. 按后果选。

第二步只写必然发生的，不写可能发生的。

## 一个例子

一个 web 服务，路由需要数据库会话。两个选项。

```python
# 选项一：会话工厂放在全局状态里，路由自己去取
@router.get("/orders/{order_id}")
async def get_order(order_id: int, request: Request) -> Order:
    async with request.app.state.session_factory() as session:
        ...


# 选项二：路由在签名里声明依赖
@router.get("/orders/{order_id}")
async def get_order(order_id: int, session: AsyncSession = Depends(get_session)) -> Order:
    ...
```

| | 全局状态 | 签名里声明 |
|---|---|---|
| 一个路由依赖什么 | 读完函数体才知道 | 读签名就知道 |
| 测试时替换依赖 | 改全局状态 | 只替换这一个依赖 |
| 新增一处使用 | 任何地方都取得到，没有记录 | 每一处都写在签名里 |

推演到这里，选择已经做完。多数项目用哪一种，没有进入这个过程。

## 前提

推导需要懂机制。不懂的时候，推出来的"必然"是想象。

不懂时遵从基准，懂了之后推导。顺序不能反。
