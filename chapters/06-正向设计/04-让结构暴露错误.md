# 让结构暴露错误

验证有两种。一种等时间给出结果，一种由结构当场给出。

能交给结构的，不留给时间。

## 两种切法

一个服务，三个业务领域，每个领域都有路由、业务逻辑、模板、数据模型。目录有两种切法。

先横切，按技术层分：

```
app/
  routers/      order.py   billing.py   inventory.py
  services/     order.py   billing.py   inventory.py
  templates/    order.py   billing.py   inventory.py
  models/       order.py   billing.py   inventory.py
```

先纵切，按领域分，领域内部再分层：

```
app/
  order/        router.py   service.py   template.py   model.py
  billing/      router.py   service.py   template.py   model.py
  inventory/    router.py   service.py   template.py   model.py
```

## 必然后果

| | 先横切 | 先纵切 |
|---|---|---|
| 跨领域调用的样子 | 同目录下的普通引用 | 跨目录的 import |
| 领域边界划错时 | 没有信号 | import 里立刻出现 |
| 耦合的走向 | 逐步累积成面条式调用 | 每一处都可见、可数 |
| 拆出一个领域 | 逐层挑文件 | 整个目录搬走 |

先横切，`services/order.py` 引用 `services/billing.py`，和引用同层任何一个文件没有区别。跨领域的耦合与层内的协作长得一样。

先纵切，跨领域的调用只能写成 `from app.billing import ...`。它在文件顶部，一眼可见。

## import 是信号

纵切之后，一条跨领域的 import 只有三种解释：

- 两个领域其实是一个。
- 被引用的东西放错了领域。
- 缺一个双方共同依赖的底层模块。

三种都是领域建模的错。写下这行 import 的代码没有错，它如实反映了模型。

这条 import 不需要评审者凭经验去发现。它是结构给出的校验结果。

## 公主生病，宫女吃药

信号指向业务架构。处理有两种。

| 处理 | 做法 | 结果 |
|---|---|---|
| 改模型 | 打回业务架构，重新划分领域 | 模型改对，这条 import 消失 |
| 改代码 | 模型不动，在代码上想办法：仅类型导入、用接口反转依赖、加一层转发、加一条豁免 | 检查通过，模型的错留在原地 |

病在领域模型，药下在代码上。

多数实际项目做不到第一种，选了第二种。

## 对人和 agent 同样生效

结构不区分读者。

- 人写出跨领域的 import，评审时看得见。
- agent 写出跨领域的 import，检查当场失败。

发现这个错，不需要任何人在场。修正这个错，要回到业务架构。

## 可插拔

纵切的领域自带全部分层，整个目录可以迁到另一个服务。

能整块搬走，说明边界是真的。搬不走，是又一个信号。

## 结构给不了的

结构暴露的是耦合的错。

这件事值不值得做，它不回答，那属于眼光。方向长期对不对，它也不回答，那只能交给时间。
